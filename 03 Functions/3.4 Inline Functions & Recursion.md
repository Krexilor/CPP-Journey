## Overview
This file covers two distinct optimization and design tools: **inline functions** (a compiler hint for performance on tiny functions) and **recursion** (a function that calls itself to solve problem through self-similar sub-steps).

## Inline Functions
Normally, calling a function involves overhead: jumping to a different memory location, pushing arguments onto the stack, and jumping back. For very small, frequently-called functions, this overhead can be larger than the function body itself.

The `inline` keyword **suggests** to the compiler that it should be replace the function call with the function's actual code directly at the call site - eliminating call overhead entirely.

```cpp
inline int square(int n) {
	return n * n;
}

int main( ) {
	int result = square(5);
	// The compiler may replace this with: int result = 5 *5;
	return 0;
}
```

> [!NOTE]
> `inline` is only a **request**, not a command. Modern compilers are extremely good at deciding when to inline functions automatically (even without the keyword) and may ignore the `inline` hint entirely - especially for functions with loops, recursion, or complex logic.

### When Inlining Helps
* Very short functions (1 - 3 lines).
* Called extremely frequently (e.g., inside tight loops).
* Simple getters/setter in classes.

> [!WARNING]
> Overusing `inline` on large functions **increases binary size** (code duplication at every call site) and can actually hurt performance due to worse CPU instruction-cache behavior. Reserve it genuinely small, hot-path functions.

## Recursion
**Recursion** occurs when a function calls itself, breaking a problem down into smaller instances of the same problem until it reaches a **base case** that stops the recursion.

## Anatomy of a Recursive Function
Every correct recursive function needs:
1. A **base case** - the condition that stops further recursion.
2. A **recursive case** - where the function calls itself with a smaller/simpler input.

```cpp
int factorial(int n) {
	if (n <= 1) {                   // Base case
	reurn 1;
	}
	return n + factorial(n - 1);    // Recursive case
}

int main( ) {
	cout << factorial(5) << endl;   // Output: 120
	return 0;
}
```

### Tracing the Call Stack
```
factorial(5)
= 5 * factorial(4)
= 5 * (4 * factorial(3))
= 5 * (4 * (3 * factorial(2)))
= 5 * (4 * (3 * (2 * factorial(1))))
= 5 * (4 * (3 * (2 * 1)))
= 120
```

> [!IMPORTANT]
> Each recursive call adds a new **stack frame** to the call stack. Without a correct base case, this leads to infinite recursion and a **stack overflow** crash. Always verify the base case is reachable from every recursive path.

### Classic Example: Fibonacci Sequence
```cpp
int fibonacci(int n) {
	if (n <= 1) return n;
	return fibonacci(n - 1) + fibonacci(n - 2);
}

int main ( ) {
	for (int i = 0; i < 8; i++) {
	cout << fibonacci(i) << " ";
	}
	return 0;
}
```

> [!WARNING]
> Naive recursive Fibonacci is extremely inefficient - `0(2^n)` time complexity, because it recalculates the same values repeatedly. This is a common interview topic for introducing **memoization** and **dynamic programming** (covered later in Algorithms).

### Recursion vs Iteration
| Aspect               | Recursion                                     | Iteration (loops)                 |
| -------------------- | --------------------------------------------- | --------------------------------- |
| Readability counting | Often Cleaner for tree/graph-like problems    | Often cleaner for simple counting |
| Memory usage         | Higher - uses the call stack                  | Lower - constant stack space      |
| Performanec          | Slightly slower (function call overhead)      | Generally faster                  |
| Best suited for      | Trees, graphs, divide & conquer, backtracking | Simple linear repetition          |

> [!TIP]
> A good rule of thumb: if a problem can be naturally expressed as "solve a smaller version of the same problem," recursion is likely the clearer choice. If it's simple repetition over a known range, prefer a loop for performance and stack safety.
