Writing code that *works* is only half the job. Code is read far more often than it is written - by teammates, by future you, and by collaborators. Clean code is a professional discipline, not an optional aesthetic preference.

## Indentation & Spacing
C++ does not enforce indentation (unlike Python), but consistent indentation is non-negotiable for readable code.

```cpp
// Bad - legal but unreadable
int main( ) {int x=5;if(x>3){cout<<"Yes";}return 0;}

// Good
int main() {
	int x = 5;
	if (x > 3) {
		cout << "Yes" << endl;
	}
	return 0;
}
```

**Standard rules:**
* Use **4 spaces** per indent level (or 2, but be consistent - never mix).
* Place the opening `{` on the same line as the statement.
* Place the closing `}` on its own line, aligned with the opening keyword.

## Naming Conventions

```cpp
// Variables & functions: camelCase
int playerHealth = 100;
double calculateDamage( ) { }

// Constants: UPPER_SNAKE_CASE
const int MAX_PLAYERS = 4;
constexpr double GRAVITY = 9.81;

// Classes & Structs: PascalCase
class PlayerCharacter { };
struct GameConfig { };
```

> [!NOTE]
>The specific convention matters less than applying it *consistently* throughout the entire codebase. Mixing styles in one project is worse than picking any single convention and sticking to it.

## Magic Numbers
A **magic number** is a raw numeric literal in code with no explanation of what it means.

```cpp
// Bad - what does 86400 mean? Why 3?
if (sessionTime > 86400) {
	spawnEnemies(3);
}

// Good - self-documenting
const int SECONDS_IN_A_DAY = 86400;
const int INITIAL_ENEMY_COUNT = 3;

if (sessionTime > SECONDS_IN_A_DAY) {
	spawnEnemies(INITIAL_ENEMY_COUNT);
}
```

> [!WARNING]
> If the same magic number appears in 10 places and needs to change, you must hunt down every occurrence. A named constant changes in one place and updates everywhere.

## Comments: When and How
Good comments explain **why**, not **what**. The code itself should explain what it's doing - if it can't, the code needs to be rewritten, not commented.

```cpp
// Bad comment - restates the code
x = x + 1;         // increment x by 1

// Good comment - explains intent
x = x + 1;         // offset by 1 because array indices are 0-based
```

## Keeping Functions Small
Each function should do **one thing**. If a function is doing multiple distinct tasks, split it.

```cpp
// Bad - this function does too much
void processGame( ) {
	// 50 lines of input handling
	// 80 lines of physics
	// 60 lines of rendering
}

// Good - each concern is isolated
void handleInput( ) { ... }
void updatePhysics( ) { ... }
void render ( ) { ... }

void processGame( ) {
	handleInput( );
	updatePhysics( ) ;
	render( );
}
```

## Code Formatting Tools
In professional C++ development, formatting is automated - nobody manually enforces spacing rules.

* **clang-format** - Industry-standard auto-formatter. Reads a `.clang-format` config file and enforces your style on save.
* **Visual Studio** - `Ctrl-K`, `Ctrl+D` formats the entire file.
* **VS Code** - `Alt+Shift+F` with the C/C++ extension installed.

> [!NOTE]
> **Key Takeaway:** Professional codebases use automated formatters to completely eliminate style debates. Set up `clang-format` early in any project and let tooling handle the formatting so you can focus on logic.
