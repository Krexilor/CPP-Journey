## Overview
All variables declared normally (e.g., `int x = 5;`) live on the **stack** - their lifetime is tied to the scope they're declared in and they're automatically destroyed when that scope ends. **Dynamic memory** lets you allocate memory on the **heap** at runtime, giving you full control over when that memory is created and when it is released - independent of any scope.

## Why Dynamic Memory?
Stack memory has two key limitations:
1. **Fixed size** - must be known at compile time (you can't declare `int arr[n]` where `n` comes from user input in standard C++).
2. **Tied to scope** - destroyed automatically when the block ends, whether you want it to or not.

Heap memory solves both: you can allocate any size at runtime, and it persists until you explicitly free it.

## `new` - Allocating on the Heap
The `new` operator allocates memory on the heap and returns a **pointer** to it.

```cpp
// Allocate a single int on the heap
int* ptr = new int;        // memory allocated, value uninitialized
int* ptr = new int(42);    // allocated and initialized to 42

cout << *ptr << endl;      // 42
```

```cpp
// Allocate a single double
double* dptr = new double(3.14);
cout << *dptr << endl;     // 3.14
```

> [!NOTE]
> Unlike stack variables, heap memory is **not automatically initialized** unless you provide a value. `new int` contains garbage: `new int(0)` or `new int{}` initializes it to zero.

## `delete` - Releasing Heap Memory
When you're done with heap memory, you **must** release it using `delete`. Failing to do so causes a **memory leak** - the memory stays allocated for the entire program lifetime even though nothing uses it.

```cpp
int* ptr = new int(42);
cout << *ptr << endl;       // 42

delete ptr;       // release the heap memory
ptr = nullptr     // immediately null the pointer (safe practice)
```

> [!WARNING]
> Forgetting to call `delete` is a **memory leak**. In long-running applications (servers, games, OS services), leaks accumulate over time until the process runs out of memory and crashes. This is one of the most common and hardest-to-debug issues in C++ programs.

## Dynamic Arrays with `new[]` and `delete`
To dynamically allocate an array whose size is determined at runtime, use `new[]`.

```cpp
int n;
cout << "Enter array size: ";
cin >> n;

int* arr = new int[n]    // allocates n ints on the heap at runtime

for (int i = 0; i < n; i++) {
	arr[i] = i * 10;
}

for (int i = 0; i < n; i++) {
	cout << arr[i] << " ";
}

delete[] arr;      // MUST use delete[] for arrays, not plain delete
arr = nullptr;
```

> [!WARNING]
> **Always match** `new[]` **with** `delete[]` - never with plain `delete`. Using `delete` on a `new[]`-allocated array is undefined behavior. It may only destroy the first element and corrupt the heap. Similarly, use plain `delete` only for single objects allocated with plain `new`.

| Allocation | Deallocation   |
| ---------- | -------------- |
| `new T`    | `delete ptr`   |
| `new T[n]` | `delete[] ptr` |

## Allocating Objects on the Heap
`new` works with any type, including classes and structs.

```cpp
struct Point {
	int x, y;
}

Point* p = new Point{3, 7};
cout << p->x << ", " << p->y << endl;    // 3, 7

delete p;
p = nullptr;
```

> [!NOTE]
> The `->` operator is shorthand for dereferencing a pointer and then accessing a member: `p->x` is equivalent to `(*p).x`. It's used whenever you access members through a pointer.

## Stack vs Heap - Side by Side

```cpp
// Stack allocation
void stackExample() {
	int x = 42;      // on the stack
	// x is destroyed automatically when this function returns
}

// Heap allocation
void heapExample() {
	int* ptr = new int(42);   // on the heap
	// ptr (the pointer variable) is destroyed when the function returns
	// but the int(42) on the heap SURVIVES - it must be deleted explicitly
	delete ptr;
}
```

| Aspect            | Stack                                | Heap                                 |
| ----------------- | ------------------------------------ | ------------------------------------ |
| Speed             | Very fast (just moves stack pointer) | Slower (general allocator overhead)  |
| Size limit        | Small (typically 1-8 MB)             | Large (limited by system RAM)        |
| Lifetime          | Tied to the enclosing scope          | Manual - you control when it's freed |
| Allocation syntax | `int x = 5;`                         | `int* ptr = new int(5)`              |
| Deallocation      | Automatic                            | Manual - `delete ptr;`               |
| Risk              | Stack overflow (too much nesting)    | Memory leaks, dangling pointers      |

## Memory Leaks in Practice

```cpp
void leakyFunction() {
	int* ptr = new int(42);
	// forgot to delete - these 4 bytes leak every time this function is called
}

int main() {
	for (int i = 0; i < 1000000; i++) {
		leakyFunction();    // 4MB leaked by the end of this loop
	}
	return 0;
}
```

> [!TIP]
> Tools like **Valgrind** (Linux/macOS) and **AddressSanitizer** (built into GCC/Clang/MSVC) can detect memory leaks and invalid memory access at runtime. These are covered in Section 19 (Debugging & Optimization). For day-to-day modern C++, **smart pointers** (`std::unique_ptr`, `std::shared_ptr`) automate deletion entirely and are the preferred solution over raw `new`/`delete`.
