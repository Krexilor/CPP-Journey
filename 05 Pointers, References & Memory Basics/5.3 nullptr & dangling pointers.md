## Overview
Two of the most dangerous pointer-related bugs in C++ are **null pointer dereferences** (following a pointer that points to nothing) and **dangling pointers** (following a pointer to memory that no longer belongs to you). Understanding both - and the safe practices to avoid them - is non-negotiable for writing reliable C++ code.

## `nullptr` - The Null Pointer
A pointer that does not currently point to any valid memory location should be set to `nullptr`. This makes its "empty" state explicit and checkable.

```cpp
int* ptr = nullptr;      // ptr points to nothing
cout << ptr << endl;     // 0 (nullptr is address 0x0)
```

> [!NOTE]
> `nullptr` was introduced in **C++11** to replace the old C-style `NULL` macro (which was just `0` or `(void*)0`). `nullptr` is type-safe - it is of type `std::nullptr_t` and won't accidentally match integer overloads the way `NULL` could. Always use `nullptr` in modern C++.

```cpp
// Old C style - ambiguous, avoid
int* ptr = NULL;

// Modern C++ - explicit and type-safe
int* ptr = nullptr;
```

## Checking Before Dereferencing
Dereferencing a `nullptr` is **undefined behaviour** - it always causes an immediate crash (segmentation fault), but the crash isn't even guaranteed, which makes it more dangerous.

```cpp
int* ptr = nullptr;
*ptr = 42           // CRASH - undefined behaviour, dereferencing null
```

Always check a pointer before dereferencing when there's any chance it could be null.

```cpp
int* ptr = nullptr;

if (ptr != nullptr) {
	cout << *ptr << endl;       // safe - only runs if ptr is valid
} else {
	cout << "Pointer is null." << endl;
}

// Shorthand (a pointer evaluates to true if non-null, false if nullptr)
if (ptr) {
	cout << *ptr << endl;
}
```

> [!IMPORTANT]
> Every pointer that doesn't yet have a valid address assigned should be initialized to `nullptr` immediately at declaration. An **uninitialized pointer** (not set to `nullptr` and not pointing to anything valid) contains a garbage address - dereferencing it is undefined behavior but won't be caught by a null check.

```cpp
int* ptr;            // DANGEROUS - garbage value, NOT null
if (ptr) { }         // might pass the check even though ptr is invalid!

int* ptr = nullptr;  // SAFE - explicitly null, always checkable
```

## Dangling Pointers
A **dangling pointer** is a pointer that once held a valid address, but the memory it pointed to has since been freed or gone out of scope. The pointer still holds the old address, but that memory no longer belongs to you.

### Case 1: Pointer to a Stack Variable That Has Gone Out of Scope

```cpp
int* getPointer() {
	int local = 42;
	return &local;      // DANGER - local is destroyed when function returns
}

int main() {
	int* ptr = getPointer();
	cout << *ptr << endl;     // undefined behavior - local is gone
	return 0;
}
```

> [!WARNING]
> Never return a pointer (or reference) to a local stack variable. That variable is destroyed when the function returns - its stack memory is reclaimed and will be overwritten by future function calls. The pointer is now dangling.

### Case 2: Pointer After `delete`

```cpp
int* ptr = new int(42);
cout << *ptr << endl;      // 42

delete ptr;                // memory freed back to the system

cout << *ptr << endl;      // UNDEFINED BEHAVIOR - memory no longer ours
ptr = nullptr;             // immediately null the pointer after deletion
```

> [!IMPORTANT]
> After calling `delete` on a pointer, **immediately set it to `nullptr`**. This prevents accidental use-after-free bugs and ensures any subsequent null check correctly identifies the pointer as invalid.
> 

### Case 3: Multiple Pointers to the Same Memory (Aliasing)

```cpp
int* ptr1 = new int(42);
int* ptr2 = ptr1;       // both point to the same memory

delete ptr1;
ptr1 = nullptr;

cout << *ptr2 << endl;  // UNDEFINED BEHAVIOR - ptr2 is now dangling
```

> [!WARNING]
> When multiple pointers alias the same heap memory, deleting through one pointer leaves all others dangling. This is one of the core motivations for **smart pointers** (`std::unique_ptr`, `std::shared_ptr`) introduced in C++11 - they handle ownership and lifetime automatically, eliminating this class of bug entirely. Smart pointers are covered in Section 11 (Modern C++).

## Double Delete
Calling `delete` on the same pointer twice is **undefined behavior** and frequently causes heap corruption or crashes.

```cpp
int* ptr = new int(42);
delete ptr;
delete ptr;      // UNDEFINED BEHAVIOR - double free
```

Setting the pointer to `nullptr` after deletion also prevents double deletes, since `delete nullptr` is safely a no-op.

```cpp
int* ptr = new int(42);
delete ptr;
ptr = nullptr;
delete ptr;      // safe - deleting nullptr does nothing
```

## Summary of Safe Pointer Practices

| Rule                                                               | Why                                       |
| ------------------------------------------------------------------ | ----------------------------------------- |
| Initialize every pointer to `nullptr` if not immediately assigned  | Prevents garbage-address dereferences     |
| Always check `if (ptr)` before dereferencing when null is possible | Prevents null dereference crashes         |
| Never return a pointer/reference to a local stack variable         | Prevents dangling stack pointers          |
| Set pointer to `nullptr` immediately after `delete`                | Prevents use-after-free and double-delete |
| Prefer smart pointers for heap memory in modern C++                | Eliminates manual ownership bugs entirely |
